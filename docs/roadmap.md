# Untangle(가칭) 웹 프로토타입 개발 로드맵

생각을 분류 부담 없이 쏟아붓고 나중에 간단히 정리하는 앱의 UX를, 1~2주 직접 사용해 검증하기 위한 웹 프로토타입 로드맵.

> 기준 문서: `docs/prd.md` (기능 ID F001~F007, F010), `docs/untangle-mvp-plan.md`

## 개요

Untangle 웹 프로토타입은 생각이 많은 ADHD 성향의 개인 사용자(본인 1인)를 위해 다음을 제공합니다.

- **빠른 입력과 나중 분류**: 한 줄씩 쏟아붓고(F001), 걱정 / 해야 할 일 / Archive / 삭제로 직접 보낸다(F002)
- **걱정 → 행동 전환과 Quick/Focus 구분**: 걱정을 행동으로 바꾸고(F004), 걸리는 시간(Quick 초록 / Focus 노랑)과 시점(오늘 / 이번 주 / 언젠가)을 고른다(F003)
- **대시보드**: iOS 위젯을 대체해 오늘 할 일과 미분류 개수를 한 화면에서 본다(F007)

로그인, 서버, DB 없이 브라우저 localStorage에만 저장합니다(F010).

## 개발 워크플로우

1. **작업 계획**
   - 기존 코드베이스를 확인해 현재 상태를 파악한다.
   - 새 작업이 생기면 이 문서를 먼저 갱신한다. 우선순위 작업은 마지막 완료 작업 바로 다음에 둔다.

2. **작업 생성**
   - 작업마다 명세, 관련 파일, 수락 기준, 구현 단계를 적는다.
   - 저장·분류 같은 비즈니스 로직 작업에는 "테스트 체크리스트"(Playwright MCP 시나리오)를 반드시 포함한다.

3. **작업 구현**
   - 작업 명세를 따라 구현하고, 단계가 끝날 때마다 진행 상황을 갱신한다.
   - 로직 작업은 Playwright MCP로 직접 눌러 보며 검증한 뒤 다음 단계로 간다.
   - 각 Task가 끝나면 멈추고 다음 지시를 기다린다.

4. **로드맵 업데이트**
   - 완료한 작업은 ✅로 표시한다.

## 진행 원칙

- **구조 우선**: 골격 → 화면(더미 데이터) → 실제 동작 순서로 만든다. 앱 전체 흐름을 일찍 눌러 볼 수 있게 한다.
- **단순함 우선**: 사용자가 Java/JavaScript에는 익숙하지만 React/Next.js/TypeScript는 낯설다. 추상화와 라이브러리를 최소화하고, 코드를 읽고 고칠 수 있는 구조를 지킨다.
- **PRD 밖 기능 금지**: AI, 우선순위, 프로젝트, 태그, 캘린더, 마감 시간, 반복, 알림, 통계, 로그인, 서버, 소셜은 만들지 않는다.
- **Task 크기**: 혼자 쓰는 프로토타입이라 한 Task는 반나절~2일 정도를 기준으로 잡는다.

## 시작 전에 정해야 할 것

| # | 항목 | 내용 |
|---|------|------|
| 1 | **프로젝트 위치** | 새 프로젝트로 분리할지, 현재 `my-app` 안에 만들지 정해야 한다. `my-app`에는 Supabase 로그인과 Google 로그인이 있고, `proxy.ts`가 비로그인 사용자를 로그인 페이지로 보낸다. "로그인·서버 없음" 원칙과 충돌하므로 `my-app`을 쓴다면 이 부분을 격리해야 한다. **결정: `my-app` 안에 구현한다.** `lib/supabase/proxy.ts` 공개 경로에 `/worries`, `/todos`, `/archive`, `/dashboard`를 추가해 로그인 없이 열리게 했다 (Task 001) |
| 2 | **열린 질문 Q4, Q7** | 어제의 "오늘" 항목 처리, 항목 문구 수정 범위가 PRD에 반영되지 않았다. Task 006 전에 확정한다 |
| 3 | **휴대폰 사용 여부** | iPhone을 대체할 앱이라 휴대폰 브라우저로 쓰고 싶을 수 있다. 그 경우 접속 방법(같은 Wi-Fi의 개발 서버 / 배포)을 Task 010에서 정한다 |

## 개발 단계

### Phase 1: 애플리케이션 골격 구축

- ✅ **Task 001: 프로젝트 위치 결정과 라우팅 골격 만들기**
  - 위 "프로젝트 위치" 결정 후 작업 폴더 확정
  - 5개 화면(브레인 덤프, 걱정, 해야 할 일, Archive, 대시보드)의 빈 페이지 파일 생성
  - 첫 화면이 브레인 덤프가 되도록 연결
  - 공통 레이아웃과 내비게이션 5개 메뉴 골격 구현
  - 수락 기준: 내비게이션으로 5개 화면을 오갈 수 있다

- ✅ **Task 002: 데이터 타입 정의**
  - "항목" 모델 타입 작성: 내용, 상태, 걸리는 시간, 언제, 원래 걱정
  - 상태(브레인 덤프 / 걱정 / 해야 할 일 / Archive), 걸리는 시간(Quick / Focus), 언제(오늘 / 이번 주 / 언젠가) 값 정의
  - 정렬용 보조 필드(생성 시각 등) 추가
  - 수락 기준: 타입을 Java 클래스 읽듯이 이해할 수 있도록 주석(한국어)을 단다

### Phase 2: UI/UX 완성 (더미 데이터 활용)

- ✅ **Task 003: 공통 컴포넌트 구현**
  - 항상 보이는 한 줄 입력창(연속 입력용)
  - 항목 카드(분류 버튼 4개 포함)
  - Quick/Focus 배지: 초록 / 노랑 색과 글자(Quick, Focus)를 함께 표시
  - 걸리는 시간·언제 선택 UI
  - 빈 상태 문구, 삭제 직후 화면 아래에 잠깐 뜨는 "되돌리기" 안내(앱 알림 기능과는 무관)
  - 더미 데이터 파일 작성

- ✅ **Task 004: 5개 페이지 UI 완성**
  - 브레인 덤프, 걱정, 해야 할 일(시점별 묶음), Archive, 대시보드를 더미 데이터로 구현
  - 걱정의 "행동으로 바꾸기" 입력 흐름과 "행동으로 옮김" 표시 구현
  - 대시보드: 오늘 할 일 목록, 미분류 개수 숫자 하나, 입력창
  - 압박 요소(완료율, 연속 기록, 빨간 지연 표시)가 없는지 확인
  - 수락 기준: 더미 데이터만으로 PRD의 사용자 여정 전체를 눈으로 따라갈 수 있다

### Phase 3: 핵심 기능 구현

- **Task 005: 브라우저 저장소 구현 (F010)** - 우선순위
  - 항목 목록을 localStorage에 읽고 쓰는 저장 모듈 작성
  - 화면 전반이 같은 저장소를 쓰도록 연결(더미 데이터 교체 지점 정리)
  - 새로고침해도 데이터가 유지되고, 저장소가 비어 있거나 깨졌을 때도 앱이 죽지 않게 처리
  - Playwright MCP로 저장·새로고침 유지 확인

- **Task 006: 빠른 입력과 분류 구현 (F001, F002, F003)**
  - 한 줄 입력 → 추가, 입력창 유지, 여러 줄 붙여넣기 시 줄마다 항목 분리
  - 걱정 / 해야 할 일 / Archive / 삭제 분류, 삭제 직후 되돌리기
  - 해야 할 일 선택 시 걸리는 시간·언제 선택 후 저장, 이후 변경
  - Playwright MCP로 입력·분류 시나리오 검증

- **Task 007: 걱정 전환, 해야 할 일 완료, Archive 구현 (F004, F005, F006)**
  - 걱정 보관, "행동으로 바꾸기"(행동 입력 → 시간·시점 선택 → 해야 할 일 생성, 원래 걱정 연결)
  - 해야 할 일을 시점별로 보여 주고, 완료하면 Archive로 이동
  - Archive: 브레인 덤프로 되돌리기, 완전히 삭제
  - Playwright MCP로 상태 이동 시나리오 검증

- **Task 008: 대시보드 구현 (F007)**
  - 오늘 해야 할 일 목록과 Quick/Focus 색 표시, 완료 처리
  - 미분류 항목 개수 표시와 브레인 덤프로 이동
  - 대시보드 입력창(F001)과 연결
  - Playwright MCP로 대시보드 갱신 확인

- **Task 008-1: 핵심 기능 통합 테스트**
  - Playwright MCP로 전체 사용자 여정 테스트: 입력 → 분류 → 행동 전환 → 완료 → Archive
  - 엣지 케이스: 빈 입력, 공백만 입력, 아주 긴 문장, 항목 0개 화면, 새로고침 직후
  - 모든 화면의 빈 상태 문구 확인

### Phase 4: 사용 준비와 다듬기

- **Task 009: 모바일 화면과 접근성 정리**
  - iPhone 크기(좁은 폭)에서 입력과 분류가 한 손으로 가능한지 확인
  - 색만으로 구분하지 않도록 Quick/Focus 글자 표시 확인, 대비와 터치 영역 점검
  - 입력창 포커스, 키보드 조작(Enter로 추가) 점검

- **Task 010: 검증 사용 준비**
  - 사용 환경 결정: PC만 / 휴대폰에서도 사용(접속 방법 정리)
  - 하루 3줄 메모 양식을 사용 문서로 정리(`docs/untangle-mvp-plan.md` 9번 기준)
  - 사용 전 데이터를 비우는 방법과 "검증 중에는 기능 추가 금지" 규칙 확인

### Phase 5: 1~2주 사용 검증

- **Task 011: 매일 사용하고 기록하기**
  - 1주 차: 입력 속도, 분류 부담, 미분류가 쌓이는 정도 확인
  - 2주 차: Quick/Focus 사용 여부, 걱정→행동 전환 횟수, 대시보드를 먼저 보게 되는지 확인
  - 하루 메모 작성(3줄)
  - 사용 중 발견한 문제는 고치지 말고 기록만 한다(검증 오염 방지). 사용을 막는 버그만 예외

- **Task 012: 회고와 iOS 이월 판단**
  - 메모를 바탕으로 iOS로 가져갈 것 / 바꿀 것 / 버릴 것 분류
  - 1주 안에 거의 열지 않게 되면 원인을 먼저 정리
  - 열린 질문 Q1~Q7의 최종 결정 기록
  - iOS 앱 기획으로 넘길 항목 정리

## 테스트 체크리스트 (Phase 3 공통, Playwright MCP)

- [ ] 한 줄을 입력하면 브레인 덤프 목록 맨 위에 추가되고 입력창이 비워진 채 유지된다
- [ ] 여러 줄을 붙여넣으면 줄마다 항목이 하나씩 생긴다
- [ ] 항목을 걱정 / 해야 할 일 / Archive로 보내면 해당 화면에 나타나고 브레인 덤프에서는 사라진다
- [ ] 삭제하면 사라지고, 직후 되돌리기를 누르면 복구된다
- [ ] 해야 할 일은 걸리는 시간·언제를 고르기 전까지 저장되지 않는다
- [ ] 걱정을 행동으로 바꾸면 해야 할 일이 생기고 원래 걱정에 "행동으로 옮김"이 표시된다
- [ ] 해야 할 일을 완료하면 Archive에 나타난다
- [ ] Archive 항목을 되돌리면 브레인 덤프로 돌아온다
- [ ] 새로고침과 브라우저 재시작 후에도 모든 항목이 유지된다
- [ ] 대시보드에는 오늘 해야 할 일과 미분류 개수만 보이고, 통계·지연 표시가 없다
